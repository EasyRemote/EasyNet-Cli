\begin{abstract}
\noindent
This appendix specifies the canonical way an agent-native system
maps a legacy world (HTTP) into the invocation graph of EasyNet,
using the act of publishing-a-folder-as-a-website as the
smallest reference instance. The construction is not a feature.
It is a paradigm: HTTP is a transport adapter for ability
invocations whose subjects are resources; the bytes a browser
receives are deterministic projections of resource state, not
opaque payloads of a private protocol. The appendix establishes
three normative invariants --- Adapter Purity, Resource
Identity, Deterministic Projection --- under which
\texttt{publish}, \texttt{fetch}, and \texttt{unpublish} form
the create / read / delete face of a Resource Execution Model
that subsequent reference systems (file storage, conversation
streams, mission outputs) inherit without re-derivation. The
implementation content from v0.5.1 is retained as §6 to witness
that the model can be realised on current EasyNet-Cli + EasyNet
infrastructure, but the load-bearing claim of v0.6 is
semantic, not engineering. The MVP --- one folder, two files
(\texttt{hello-world.html}, \texttt{style.css}), one browser
fetch, one kernel-enforced sandbox --- is the existence proof.
\end{abstract}

\textbf{v0.5.1} & \textbf{v0.6} \\

\section{The paradigm}
\label{sec:paradigm}

\subsection{Statement}

\normsv{}\textbf{HTTP is a transport adapter for
agent-native invocations.} A browser GET on a published page is
not a new protocol surface; it is a transport rendering of the
invocation tuple
\(\texttt{invoke}(\textit{caller}, \textit{callee},
\textit{ability}, \textit{subject}, \textit{nonce},
\textit{causal\_context}, \textit{args})\) whose
\textit{ability} is a project-owned read primitive, whose
\textit{subject} is the project's resource identity, and whose
returned payload is a deterministic projection of that
resource's state.

\subsection{The Resource Execution Model}
\label{sec:rem}

\derived{} The minimal mechanism the paradigm requires:

\begin{lstlisting}
State        :   Resource
Transition   :   Ability
Invocation   :   f(resource, args)
Receipt      :   proof of transition

publish      =   create(resource)        canonical, state-changing
fetch        =   read(resource)          operational, state-preserving
unpublish    =   delete(resource)        canonical, state-changing
\end{lstlisting}

A reference system is a concrete instantiation of this model.
This appendix specifies the \texttt{pages} reference system; the
companion appendix A specifies the \texttt{page} reference
system (single document); future RFC-006-C\,..\,F will
instantiate further reference systems (file storage,
conversation streams, mission outputs, agent-built API surfaces)
on the same Model.

\begin{notebox}
The Model is intentionally narrower than ``everything that has
URA''. Not every resource is a Resource-Execution-Model citizen;
only those for which a system declares
\texttt{create/read/delete} primitives over the resource and
binds them to ability URIs. v0.6 establishes Pages as the first
such instantiation; v0.7 will lift the Model to a standalone
specification that this appendix references.
\end{notebox}

\subsection{The minimum reference instance: pages}

\derived{} Among possible Resource-Execution-Model
instantiations, ``publishing a folder of static bytes for HTTP
fetch'' is the smallest one with all four ingredients: a
resource (the project), a state (the published bytes), three
clear transitions (publish/fetch/unpublish), and a legacy
transport (HTTP) that must enter the invocation graph through
the adapter.

It is therefore the canonical first instance. Anything more
ambitious adds payload, not paradigm. Anything less ambitious
omits a transition class (e.g., a system without \texttt{delete}
cannot witness the resource's full lifecycle).

\section{Assumptions}
\label{sec:assumptions}

\normsv{} v0.6 is written under the following assumptions. Each
is stated explicitly so that downstream implementation work
(URA v2 plan, admission upgrades, receipt persistence) can be
discharged independently while this appendix's semantic claims
remain stable.

\begin{assumptionbox}[A-1: Resource identity exists]
There exists, in EasyNet, a notion of resource identity
\texttt{resource/<id-part>/<path-part>} satisfying URA v4.1.5
§A.URA-7 (three URA segments). The identity is consumable by
admission, by receipts, and by the ability registry. Whether
the identity is content-addressed or user-defined is an
INV-2 question; whether it is enforced today by ent schema or
deferred to URA v2 plan §Phase 2 is an implementation
question and does not affect this appendix.
\end{assumptionbox}

\begin{assumptionbox}[A-2: Admission enforces \texttt{subject\_kinds}]
For each ability registered in EasyNet, the ability contract
declares a \texttt{subject\_kinds} whitelist; admission rejects
invocations whose subject URA kind is not in the whitelist.
Whether the enforcement is in code today or pending URA v2 plan
§Phase 5 does not affect this appendix.
\end{assumptionbox}

\begin{assumptionbox}[A-3: Receipts can be chained]
The receipt store can record a receipt's \texttt{prev\_receipt\_hash}
and walk the chain backwards from a leaf receipt. Whether
chain-walking is in production today or pending URA v2 plan
§Phase 6 does not affect this appendix; INV-3's verification
machinery uses chain-walking, but a non-walking store still
satisfies the read-side invariants v0.6 places on individual
receipts.
\end{assumptionbox}

\begin{assumptionbox}[A-4: Ability ownership widens to \(\{\)user, agent, hub, resource\(\}\)]
The ontology theorem in
\texttt{ONTOLOGY\_AGENT\_ABILITY.md} §3.2 states ``Ability
belongs to exactly one Agent.'' v0.6 assumes the equivalent
post-amendment statement: ``Ability belongs to exactly one of
\(\{\)user, agent, hub, resource\(\}\).'' The Phase B
amendment (this plan) discharges this assumption. Until it
lands, v0.6 reads the wider claim into v4.1.5 ability URI
grammar (whose tail is already \texttt{<owner-id>.<name>}, with
\texttt{<owner-id>} typed as ``the URA kind that names the
owner'').
\end{assumptionbox}

\section{The three normative invariants}
\label{sec:invariants}

\subsection{INV-1 --- Adapter Purity}

\begin{invariant}[INV-1: Adapter Purity]
\texttt{ability/01HUB.pages.serve}, the ability that bridges
HTTP into the invocation graph for the \texttt{pages} reference
system, \textbf{MUST} be a pure transport adapter. Specifically:
\begin{itemize}[leftmargin=2em,itemsep=0.1em]
    \item It \textbf{MUST NOT} mutate any resource state.
    \item It \textbf{MUST NOT} emit canonical receipts.
    \item It \textbf{MAY} emit operational receipts (lossy
    observability) recording the HTTP request that triggered the
    forwarded invocation.
    \item It \textbf{MUST} delegate the read entirely to the
    project-owned ability
    \texttt{<user>.<project>.page.fetch} via the standard
    \texttt{forward\_invoke} dispatch path.
    \item It \textbf{MUST NOT} cache or transform the bytes
    returned by \texttt{page.fetch}, beyond mechanical HTTP
    framing (Content-Type, Content-Length, ETag derivation
    from byte hash).
\end{itemize}
\end{invariant}

\derived{} Adapter Purity is the invariant that prevents the
HTTP transport from accidentally becoming a parallel state
plane. Without it, a Hub implementation could (a) mutate
project state during a serve, (b) record state-changing
canonical receipts that did not originate from a project's own
ability, or (c) introduce side-channels through which an
operator could publish bytes without ever invoking
\texttt{publish}. Adapter Purity rules these out at the
specification layer, before they can arise at the
implementation layer.

\subsection{INV-2 --- Resource Identity}

\begin{invariant}[INV-2: Resource Identity]
Every published project \textbf{MUST} correspond to a resource
identity expressed as a v4.1.5-conformant URA. The identity has
two valid forms:
\begin{itemize}[leftmargin=2em,itemsep=0.1em]
    \item \textbf{v0 transitional form (this appendix).} The
    identity is user-defined: \texttt{resource/<user>.<project>}.
    Uniqueness is enforced per user at publish time. This form
    is acceptable for single-host serve where federation is not
    yet exercising the identity.
    \item \textbf{v1 mandatory form (next appendix revision).}
    The identity \textbf{MUST} be content-addressed: the
    \texttt{<project>} component is the prefix of a Merkle hash
    over the canonicalised folder content. Aliases (mutable
    names pointing at content hashes) are first-class, the way
    Git refs name commits.
\end{itemize}
v0 publishes \textbf{MUST} record their transitional status in
the publish receipt's \texttt{state\_transition} payload so that
a future verifier can distinguish a v0 publish from a v1 one.
\end{invariant}

\derived{} INV-2 separates ``the resource exists'' from ``the
resource has a stable, verifiable identity.'' v0 publishes are
useful for development and single-host operation but are not
sufficient for federation, audit, or third-party caching. v1's
content-addressed form is what makes the resource a citizen of
the network rather than a folder on Alice's laptop.

\begin{warningbox}
INV-2 explicitly declares that v0 is transitional. A v0 system
without a clear v1 migration path would not be conformant. The
URA v2 plan §Phase 6 (content-addressed blob store) provides
the substrate for v1's identity computation; the migration is
mechanical once that substrate exists.
\end{warningbox}

\subsection{INV-3 --- Deterministic Projection}

\begin{invariant}[INV-3: Deterministic Projection]
\texttt{ability/<user>.<project>.page.fetch} \textbf{MUST} be a
deterministic projection of the project's resource state. For
a given resource identity \(R\) and request path \(p\):
\[
    \texttt{fetch}(R, p) = \texttt{bytes}(R, p)
\]
where \(\texttt{bytes}(R, p)\) is fully determined by \(R\) and
\(p\) and contains no host-, time-, or environment-dependent
components.

\noindent It follows that:
\begin{itemize}[leftmargin=2em,itemsep=0.1em]
    \item Two hosts that both claim resource identity \(R\)
    \textbf{MUST} return byte-identical responses for the same
    \(p\).
    \item A receipt for \texttt{fetch(R, p)} \textbf{MUST}
    bind \(R\), \(p\), and \(\text{sha256}(\texttt{bytes})\)
    so a verifier auditing the chain can confirm the projection
    invariant after the fact.
    \item \texttt{fetch} \textbf{MUST NOT} introduce dynamic
    content (timestamps, IP-derived data, randomised banners).
    Such content belongs to a different ability whose contract
    explicitly admits non-determinism.
\end{itemize}
\end{invariant}

\derived{} INV-3 is the invariant that makes the Resource
Execution Model federate. Without it, two hosts claiming the
same resource identity may return different bytes; with it, a
caller (or a third-party CDN) can rely on identity alone for
content equivalence. It is also the invariant that makes
content-addressed resource identity (INV-2 v1) verifiable: the
hash of the projection equals the hash that names the resource.

\begin{notebox}
INV-3 does not forbid all dynamic web content; it forbids
dynamic content from \texttt{page.fetch}. A reference system
that needs dynamic content (e.g., personalised dashboards) must
introduce a separate ability whose contract declares
non-deterministic projection, and the bytes from that ability
flow through a different HTTP route (not under
\texttt{*.*.pages.<realm>}) so callers know to expect
non-determinism.
\end{notebox}

\subsection{Why these three, no fewer, no more}

\derived{} Following the degeneracy method of AXIOM.tex §why-six:

\begin{itemize}[leftmargin=2em,itemsep=0.18em]
    \item \textbf{Without INV-1}, the HTTP boundary becomes a
    second authoritative state plane. Any operator with access
    to the Hub's process can rewrite project state without
    invoking \texttt{publish}. The receipt chain is no longer
    the single source of truth.
    \item \textbf{Without INV-2}, two systems can claim the
    same name for different bytes. Federation collapses;
    third-party caching is unsafe; receipts cannot be verified.
    \item \textbf{Without INV-3}, identical names on two hosts
    return different bytes. Content cannot be cached without
    consulting an authoritative origin; the Hub is forced into
    a pull-through cache role, which contradicts INV-1's
    purity.
\end{itemize}

Each invariant blocks a class of failure that the others do
not address; removing any one collapses the model.

\section{State transition model in detail}
\label{sec:transitions}

\subsection{publish: create(resource)}

\normsv{} \texttt{publish} is the canonical transition that
creates a project resource and registers its
\texttt{page.fetch} ability.

\begin{lstlisting}
caller   = caller_uri                       (typically the publishing user
                                             or one of their agents)
callee   = callee_uri                       (the user URA hosting the project)
ability  = ability/<user>.pages.publish
subject  = user/<user>                      (creating-self transition;
                                             the project resource does not
                                             yet exist)
args     = {
    folder:        absolute path on owner host,
    project_id:    URA-safe segment (v0 transitional, v1 derived),
    visibility:    "public" | "private" | "scoped"
}
\end{lstlisting}

\textbf{Pre-state}: no resource with identity
\texttt{resource/<user>.<project>} exists.

\textbf{Post-state}: a resource with that identity exists; an
ability \texttt{ability/<user>.<project>.page.fetch} is
registered; the resource's bytes are (semantically) the
content of the published folder.

\textbf{Receipt class}: canonical (state-changing). The
receipt's \texttt{state\_transition} payload \textbf{MUST}
carry:

\begin{itemize}[leftmargin=2em,itemsep=0.1em]
    \item \texttt{post\_resource\_uri}: the minted resource URA
    \item \texttt{identity\_form}: \texttt{"v0\_user\_defined"}
    or \texttt{"v1\_content\_hash"} (per INV-2)
    \item \texttt{visibility}
    \item if v1: \texttt{content\_hash} (full sha256, not just prefix)
\end{itemize}

\subsection{fetch: read(resource)}

\normsv{} \texttt{fetch} is the operational transition that
reads bytes from the project resource.

\begin{lstlisting}
caller   = caller_uri                       (typically hub/01HUB during
                                             HTTP-adapted invocation)
callee   = callee_uri                       (host agent of the project)
ability  = ability/<user>.<project>.page.fetch
subject  = resource/<user>.<project>/<path>
args     = { path: <path> }
\end{lstlisting}

\textbf{Pre-state}: resource exists; \texttt{<path>} resolves
to a regular file inside the published root (per the read
sandbox below).

\textbf{Post-state}: identical to pre-state. \texttt{fetch}
mutates nothing.

\textbf{Receipt class}: operational (state-preserving). Per
INV-3, the receipt \textbf{MUST} bind \texttt{<path>} and
\texttt{sha256(bytes)}; the byte hash makes the projection
invariant verifiable from the receipt alone.

\subsection{unpublish: delete(resource)}

\normsv{} \texttt{unpublish} is the canonical transition that
revokes the resource.

\begin{lstlisting}
caller   = caller_uri
callee   = callee_uri                       (host agent of the project)
ability  = ability/<user>.pages.unpublish
subject  = resource/<user>.<project>
args     = {}
\end{lstlisting}

\textbf{Pre-state}: resource with the given identity exists.

\textbf{Post-state}: resource no longer exists; the project's
\texttt{page.fetch} ability is unregistered; subsequent
\texttt{fetch} attempts fail with the standard
``no such ability'' admission rejection.

\textbf{Receipt class}: canonical. The receipt's
\texttt{state\_transition} payload binds the pre-state
\texttt{content\_hash} (when known) so the deletion is itself
auditable: a verifier walking the chain knows what bytes
existed at the moment of revocation.

\subsection{Read sandbox: a semantic obligation, not an implementation detail}

\normsv{} The read sandbox is the mechanism by which INV-3
becomes enforceable in practice. \texttt{page.fetch}'s callee
\textbf{MUST} restrict path resolution to the published folder
root using a kernel-enforced contract:

\begin{itemize}[leftmargin=2em,itemsep=0.1em]
    \item Path resolution \textbf{MUST NOT} escape the
    folder root, regardless of \texttt{..} components,
    symbolic links, or filesystem mutations between calls.
    \item The contract \textbf{MUST} be at the kernel layer
    (e.g., \texttt{openat2(2)} with
    \texttt{RESOLVE\_BENEATH | RESOLVE\_NO\_SYMLINKS} on Linux),
    not at the user-space layer
    (\texttt{realpath()}+prefix-check), because user-space
    checks race the filesystem (TOCTOU).
\end{itemize}

The sandbox is not a security feature added on top of the
Model; it is the mechanism by which the Model's deterministic
projection (INV-3) holds against adversarial inputs. A path
that the kernel refuses to resolve cannot be a member of the
projection's domain.

\section{Receipt semantics}
\label{sec:receipts}

\subsection{Two tiers, derived from the Model}

\normsv{} The transitions in §\ref{sec:transitions} sort
naturally into two receipt classes:

\begin{center}
\renewcommand{\arraystretch}{1.18}
\begin{tabularx}{\linewidth}{l X X}
\toprule
\textbf{Tier} & \textbf{For transitions that are} & \textbf{Used by} \\
\midrule
Canonical
 & state-changing (publish, unpublish)
 & \texttt{prev\_receipt\_hash} chain; persistent; walkable \\
Operational
 & state-preserving (fetch, serve)
 & lossy ring buffer; observability; aggregable rates \\
\bottomrule
\end{tabularx}
\end{center}

The classification is not a heuristic; it is a direct
consequence of the Resource Execution Model. Canonical
transitions advance state and therefore must be durably
recorded for audit. Operational transitions read state without
advancing it and would saturate the canonical chain under any
realistic load (an SPA visit yields tens of fetches per
session); their receipts are observability artefacts, not
state-history artefacts.

\subsection{What receipts witness, in this reference system}

\normsv{} For each transition class:

\begin{itemize}[leftmargin=2em,itemsep=0.18em]
    \item \textbf{publish receipt} witnesses ``user \(U\)
    minted resource \(R\) with content \(H\) at time \(t\),
    visibility \(V\)''.
    \item \textbf{unpublish receipt} witnesses ``user \(U\)
    revoked resource \(R\) (last known content \(H\)) at time
    \(t'\)''.
    \item \textbf{fetch receipt} witnesses ``a request for
    path \(p\) on resource \(R\) returned bytes whose hash is
    \(h_p\)''. By INV-3, two hosts that both claim \(R\) must
    produce the same \(h_p\) for the same \(p\) --- a
    verifier comparing two operational receipts can detect
    deterministic-projection violation.
    \item \textbf{serve receipt (optional)} witnesses ``the
    Hub received an HTTP request for \(R/p\) at time \(t\)
    and forwarded it to callee \(C\)''. By INV-1, this receipt
    carries no state-change information; it is purely
    observability.
\end{itemize}

\subsection{Linkage to URA v2 plan}

\derived{} The receipt-store substrate the URA v2 plan §Phase 6
introduces (chain walking, indexed by subject URA, indexed by
ability URA) is exactly the substrate this RFC's receipts
inhabit. v0.6 makes no demands on receipt encoding beyond what
URA v2 plan delivers; conformance to v0.6 requires only that
the canonical/operational distinction is honoured.

% ──────────────────────────────────────────────────────────────────────────
\section{URL = invocation, in this reference system}
\label{sec:url}

\subsection{The transformation}

\normsv{} The Hub binds a wildcard host pattern,
\texttt{*.*.pages.<realm>}, on its TLS listener. An HTTP
request:

\begin{lstlisting}
GET /<path> HTTP/1.1
Host: <project>.<user>.pages.<realm>
\end{lstlisting}

is translated, by \texttt{ability/01HUB.pages.serve}, into:

\begin{lstlisting}
caller   = hub/01HUB
callee   = callee_uri (host of <user>.<project>)
ability  = ability/<user>.<project>.page.fetch
subject  = resource/<user>.<project>/<path>
args     = { path: "<path>" }
\end{lstlisting}

The transformation is mechanical:

\begin{itemize}[leftmargin=2em,itemsep=0.12em]
    \item Subdomain \texttt{<project>.<user>} \(\to\)
    URA id-part \texttt{<user>.<project>} (URL leads with
    project for human readability; URA leads with user for
    owner-first identity).
    \item URL path \(\to\) URA path-part verbatim.
    \item HTTP method \texttt{GET} \(\to\) \texttt{page.fetch}
    (the only verb in this reference system; non-GET methods
    are rejected at the Hub).
\end{itemize}

\subsection{Why this is not just a routing rule}

\derived{} By INV-1, the Hub's serve ability does not own the
read; it only forwards. By INV-3, the bytes the Hub returns
are the same bytes any other client of \texttt{page.fetch}
receives. Together, INV-1 + INV-3 mean that the URL form is a
projection of the URA form: every URL has a URA, every URL's
response equals the URA's invocation result, and the
correspondence is verifiable through the receipt chain.

This is the load-bearing claim of the paradigm. HTTP is no
longer ``the API''; it is a viewing surface onto the
invocation graph.

\section{Reference implementation (informative)}
\label{sec:ref-impl}

\textit{This section is non-normative. It witnesses that the
v0.6 specification can be realised on current EasyNet-Cli +
EasyNet infrastructure, using the addressing form, sandbox
mechanism, and receipt classification preserved from v0.5.1.
Conforming implementations are not required to follow these
specific choices.}

\subsection{Inherited from v0.5.1}

The v0.5.1 implementation surface is preserved in this
section: ability namespace formation
(\texttt{<user>.<project>.page.fetch}), URL form
(\texttt{<project>.<user>.pages.<realm>/<path>}), the
\texttt{openat2(2)} + \texttt{RESOLVE\_BENEATH} sandbox, the
allow-list MIME table, the in-daemon Axum listener for MVP and
the Go-backend Hub for production, the
\texttt{forward\_invoke} dispatch path, the bounded operational
receipt ring buffer.

The implementation details retained from v0.5.1 are consolidated
below. This v0.6 document is the only canonical specification;
deleted historical snapshots are not normative inputs to an
implementation or conformance review.

\subsection{The MVP: a witness, not a deliverable}

\normsv{} The minimum existence proof of v0.6 is a folder with
two files (\texttt{hello-world.html}, \texttt{style.css}),
served through an in-daemon Axum listener bound to
\texttt{127.0.0.1:8787}, fetched by a real browser, and
verified via a kernel-traced path-traversal attempt that
returns 404 without the daemon ever issuing a syscall against
the target file outside the sandbox.

The MVP is not a product. It is the simplest test that
discharges all three invariants simultaneously: Adapter Purity
(the Hub forwards to the project's ability and emits no
canonical receipt), Resource Identity (the project mints a v0
identity that admission accepts as a resource subject), and
Deterministic Projection (the bytes a browser receives equal
the bytes the daemon reads from the published folder, sha256
verified).

\subsection{Test stratification}

\normsv{} Three matrices, each layered three deep:

\begin{itemize}[leftmargin=2em,itemsep=0.15em]
    \item \textbf{Matrix A (unit/integ, in-process)}: 13 cases
    covering each transition's success and failure paths,
    each invariant's enforcement, and concurrent fetches /
    file-size cap edge cases.
    \item \textbf{Matrix B (CLI surface, out-of-process)}: 10
    cases covering the \texttt{easynet pages
    \{create,list,show,delete,url\}} subcommand surface, JSON
    vs human output, exit codes.
    \item \textbf{Matrix C (Docker e2e, real container, real
    syscall trace)}: 10 cases including a \texttt{strace}
    sidecar that asserts the kernel never reads files outside
    the published folder during a path-traversal attack.
\end{itemize}

A phase ships only when every case in every matrix passes at
all three layers (process / wire / state). The matrices are
specified in detail in the implementation plan
(\texttt{vectorized-cooking-sparkle.md}) and not duplicated
here.

\section{Beyond the reference system}
\label{sec:beyond}

\subsection{What this RFC unlocks (without specifying)}

\derived{} With Pages established as the first reference
realisation of the Resource Execution Model, four immediate
extensions become routine:

\begin{enumerate}[leftmargin=2em,itemsep=0.15em]
    \item \textbf{Files} (RFC-006-C, projected). A
    \texttt{file} resource kind, with the same publish /
    fetch / unpublish triple, but no HTTP adapter --- the
    fetch surface is direct ability invocation. INV-1 still
    holds vacuously (no adapter); INV-2 + INV-3 transfer
    unchanged.
    \item \textbf{Conversations} (RFC-006-D, projected). A
    \texttt{conversation} resource kind whose \texttt{fetch}
    surface returns a deterministic projection of the
    conversation state at a specific receipt id (immutable
    snapshot semantics); state transitions are
    message appends.
    \item \textbf{Mission outputs} (RFC-006-E, projected). A
    \texttt{mission\_output} resource kind whose state is the
    JSON of the mission's terminal step receipt; \texttt{fetch}
    returns the JSON. Aliasing (mutable name pointing at a
    specific receipt) is the natural ``latest run'' shape.
    \item \textbf{Agent-built API surfaces} (RFC-006-F,
    projected). A \texttt{web\_app} resource kind that
    composes \texttt{page} (static bytes) with non-static
    abilities (\texttt{<user>.<project>.api.<verb>}). INV-1's
    purity confines the static side; the API side declares
    its own non-determinism (INV-3 does not bind it).
\end{enumerate}

Each of the above is purely additive: they instantiate the
Model without changing it. The paradigm scales horizontally
through reference systems, not vertically through ad-hoc
extensions.

\subsection{What this RFC deliberately leaves to future work}

\deferred{}

\begin{itemize}[leftmargin=2em,itemsep=0.15em]
    \item \textbf{INV-2 v1 enforcement} (content-addressed
    project ids). v0.6 ships under the v0 transitional form;
    v0.7 (or RFC-006-B-Phase-3 in the implementation plan)
    flips the requirement.
    \item \textbf{Visibility = PRIVATE / SCOPED}.
    Capability-URL semantics, full-hash project ids,
    admission policies for SCOPED. The Resource Execution
    Model has room for these but does not specify them.
    \item \textbf{HTTP/2 / HTTP/3 / WebSocket / SSE
    semantics under the same paradigm}. Adapter Purity should
    extend mechanically, but the receipt-tier classification
    of long-lived connections is non-trivial; future work.
    \item \textbf{The Resource Execution Model as a
    standalone specification.} v0.6 introduces the Model in
    service of Pages; v0.7 promotes it to an independent RFC
    that this appendix references.
\end{itemize}
